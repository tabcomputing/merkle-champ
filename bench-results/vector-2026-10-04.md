# Vector benchmark summary, 2026-10-04

Note (2026-10-05): `Vector` was replaced by the content-defined `Sequence`
(FORMAT.md section 10; bench-results/sequence-2026-10-05.md). These figures
are kept for the record.

Machine: Intel Core Ultra 7 155H, Linux, Rust 1.90, release build, pinned to one CPU
(`taskset -c 2`). One process run of `examples/vector_bench.rs`; each figure is the
median of seven samples after a warm-up, in nanoseconds per operation unless
marked. Elements are `u64`. imbl's `Vector` is an RRB tree with no content
identities, so its identity row is "layered": hashing every element in order,
which is what a store would have to do per request.

| Workload | Size | Vector | imbl Vector | std Vec |
|---|---:|---:|---:|---:|
| build from an iterator, per element | 10k | 1.8 | 10.7 | 0.2 |
| build from an iterator, per element | 1M | 1.8 | 10.0 | 0.2 |
| get, random index | 10k | 2.7 | 13.5 | 0.3 |
| get, random index | 1M | 6.8 | 20.1 | 0.3 |
| iterate, per element | 1M | 0.7 | 2.0 | 0.1 |
| set, old version kept | 10k | 404 | 753 | — |
| set, old version kept | 1M | 857 | 1,957 | — |
| set, sole owner | 1M | 35 | 48 | — |
| push then pop, sole owner | 1M | 9.5 | 9.2 | — |
| first identity, cold | 1M | 12.9 ms | — | — |
| identity after one write | 10k | 1.8 µs | 0.11 ms, layered | — |
| identity after one write | 1M | 3.2 µs | 11.1 ms, layered | — |

## Reading

- Faster than imbl's RRB vector on every read and write here, and equal on
  push and pop. The dense trie is shallower and simpler to walk; imbl pays
  for its relaxed nodes, which buy O(log n) concatenation and slicing this
  crate does not offer.
- Identity after a write: about 3,400x faster than rehashing every element
  at 1M, because only the changed path is rehashed. As with merkle-champ, this
  is the property a content-addressed store needs.
- The building rows use `Builder` (through `collect`), which fills leaves in
  place.

## Packed leaves (later the same day)

Fixed-width numbers now fill 1 KB leaves with their bytes (FORMAT.md, section
10.2): 128 `u64` to a leaf instead of 32. Same machine and method; the `u64`
rows before and after, at 1M elements:

| Workload | 32 to a leaf | 128 packed |
|---|---:|---:|
| build from an iterator, per element | 1.8 | 1.1 |
| get, random index | 6.8 | 4.8 |
| iterate, per element | 0.7 | 0.4 |
| set, old version kept | 857 | 684 |
| set, sole owner | 35 | 39.5 |
| push then pop, sole owner | 9.5 | 8.4 |
| first identity, cold | 12.9 ms | 4.67 ms |
| identity after one write | 3.2 µs | 2.8 µs |

Bytes, 1,024 to a leaf, against `std::Vec<u8>`, whose content identity is a
flat SHA-256 of the whole buffer:

| Workload, 1M bytes | `Vector<u8>` | `Vec<u8>` |
|---|---:|---:|
| build from an iterator, per byte | 0.71 | 0.02 |
| get, random index | 2.88 | 0.31 |
| iterate, per byte | 0.33 | 0.10 |
| first identity, cold | 0.55 ms | 0.43 ms |
| identity after one write | 2.6 µs | 429 µs |

Packing is faster on nearly every row: fewer, wider leaves make the tree
shallower, and hashing a leaf's bytes in one pass beats encoding each element.
A sole owner's `set` costs a little more. For bytes, the first identity costs
28% more than hashing the buffer flat, and every identity after a write about
165 times less.
